# Plan: Port data isolation + idempotency from jwt-demo to jwt-demo-reactive

## Context

Two recent PRs in the blocking `jwt-demo` project added significant features:
- **PR #65**: Row-level data isolation by `auth_client_id` via M:N `client_access` join table
- **PR #66**: Idempotency key support with request lifecycle tracking for balance updates

This plan ports both features to the reactive project, adapting for R2DBC (native SQL, reactive streams, different exception types).

---

## Feature 1: Row-level data isolation by auth_client_id

**Goal**: Each OAuth2 client only sees clients and accounts it has access to. The `client_access` join table maps `(client_id, auth_client_id)` so multiple systems can share access to the same client record. Phone uniqueness remains global.

### Step 1.1 — DB migration

**New file**: `V6__create_client_access_table.sql`

```sql
CREATE TABLE client_access (
    client_id       BIGINT NOT NULL REFERENCES client(id),
    auth_client_id  VARCHAR(255) NOT NULL,
    PRIMARY KEY (client_id, auth_client_id)
);

CREATE INDEX idx_client_access_auth_client_id ON client_access(auth_client_id);
```

### Step 1.2 — Entity + repository for ClientAccess

**New files**:
- `model/ClientAccess.java` — R2DBC entity mapped to `client_access` table with `@Table("client_access")`
- `model/ClientAccessId.java` — Composite key record `(Long clientId, String authClientId)` implementing `Serializable`
- `repository/ClientAccessRepository.java` — `R2dbcRepository<ClientAccess, ClientAccessId>` with `Mono<Boolean> existsByClientIdAndAuthClientId(Long clientId, String authClientId)`

Note: R2DBC composite keys use `@IdClass` on the entity + two `@Id @Column` fields, same pattern as JPA.

- Replace `searchByNameOrSurname` with `searchByNameOrSurnameAndAuthClientId` that JOINs `client_access` and filters by `authClientId`

## Feature 2: Idempotency key support for balance updates

**Goal**: Add `idempotencyKey` to `UpdateBalanceRequest` for idempotent balance change requests. Track balance operations in the `request` table with status lifecycle.

### Step 2.1 — DTO update

**File**: `dto/UpdateBalanceRequest.java`

Add nullable `UUID idempotencyKey` field as first record component:
```java
public record UpdateBalanceRequest(
    @Schema(description = "Idempotency key for idempotent request tracking")
    UUID idempotencyKey,
    @NotNull(message = "{validation.clientId.required}") Long clientId,
    @NotNull(message = "{validation.amount.required}") BigDecimal amount
) {}
```

### Step 2.2 — DB migration

**New file**: `V7__add_balance_update_request_types.sql`

```sql
ALTER TABLE request DROP CONSTRAINT chk_request_type;
ALTER TABLE request ADD CONSTRAINT chk_request_type
    CHECK (type IN ('CLIENT_CREATE', 'UPDATE_BALANCE_PESSIMISTIC', 'UPDATE_BALANCE_OPTIMISTIC', 'OTHER'));
```

### Step 2.3 — RequestType enum

**File**: `model/RequestType.java`

Add `UPDATE_BALANCE_PESSIMISTIC`, `UPDATE_BALANCE_OPTIMISTIC`.

### Step 2.4 — New exception + messages

**New file**: `exception/AccountUpdateInProgressException.java`
- Runtime exception with `UUID requestId`, `getMessageCode()` → `"error.account.updateInProgress"`

**File**: `exception/GlobalExceptionHandler.java`
- Add handler → 409 CONFLICT

**Files**: `messages.properties`, `messages_en.properties`, `messages_ru.properties`
- Add `error.account.updateInProgress` and `error.account.updateFailed`

### Step 2.5 — RequestService new methods

**File**: `service/RequestService.java`

Add methods:
- `Mono<CreateRequestResult> createPendingRequestIfAbsent(UUID idempotencyKey, Object payload, RequestType type, String authClientId)` — create or match existing request, return status + saved response data
- `Mono<Void> completeRequest(UUID requestId, String authClientId, String responseData)` — mark COMPLETED
- `Mono<Void> failRequest(UUID requestId, String authClientId, String errorData)` — mark FAILED
- `boolean jsonEquals(String json1, String json2)` — semantic JSON comparison

Add inner record: `CreateRequestResult(UUID requestId, boolean alreadyExisted, RequestStatus status, String savedResponseData)`

The `createPendingRequestIfAbsent` should run in a **REQUIRES_NEW** transaction so the request record is committed independently of the balance operation. Use `@Transactional(propagation = Propagation.REQUIRES_NEW)`.

### Step 2.6 — AccountService wrap with request lifecycle

**File**: `service/AccountService.java`

Major changes:
- Inject `RequestService`, `SecurityService`, `ObjectMapper`
- `updateBalancePessimistic(request)`: no longer takes `authClientId` param (extracted from SecurityService internally)
  1. Call `requestService.createPendingRequestIfAbsent(...)` with REQUIRES_NEW
  2. If `alreadyExisted` → delegate to `handleExistingRequest(result)`
  3. Otherwise, execute balance update, then `requestService.completeRequest(...)`
  4. On error → `markRequestFailed(...)` then rethrow
- `updateBalanceOptimistic(request)`: same pattern, wrapping `safeUpdate`
- `safeUpdate(...)`: add `requestId` + `requestAuthClientId` params, call `completeRequest` inside the transaction
- New `handleExistingRequest(CreateRequestResult)`:
  - `COMPLETED` → deserialize and return saved response
  - `FAILED` → rethrow stored exception
  - `PENDING`/`PROCESSING` → throw `AccountUpdateInProgressException`
- New `StoredError` record: `(int code, String message, String exceptionType, Long clientId)`
- New `markRequestFailed(...)` helper: stores typed error info, wraps `failRequest` in try-catch

### Step 2.7 — AccountController simplification

**File**: `controller/AccountController.java`

Since `AccountService` now handles `authClientId` internally via `SecurityService`, controller methods become simpler:
```java
public Mono<AppResponse<AccountResponse>> updateBalancePessimistic(...) {
    return accountService.updateBalancePessimistic(request).map(AppResponse::ok);
}
```

Note: The controller still injects `SecurityService` for `getByClientId`, but balance update methods don't need to pass `authClientId` anymore.

Add `@ApiResponse(responseCode = "409", ...)` for idempotency conflict on both balance endpoints.

2. **Feature 2 second** (idempotency) — builds on the authClientId infrastructure from Feature 1

## Key reactive adaptation notes

| Concern | Blocking (JPA) | Reactive (R2DBC) |
|---|---|---|
| Entity composite key | `@IdClass(ClientAccessId.class)` | Same pattern works with R2DBC |
| JPQL queries | `@Query("SELECT ... JOIN ...")` | Native SQL with `@Query("SELECT ...")` |
| Transaction isolation | `@Transactional(propagation = REQUIRES_NEW)` | `@Transactional(propagation = REQUIRES_NEW)` (works with reactive TM) |
| Duplicate key on insert | `DataIntegrityViolationException` | `DuplicateKeyException` (Spring wraps R2DBC) |
| Pessimistic lock | `@Lock(LockModeType.PESSIMISTIC_WRITE)` + JPQL | `FOR UPDATE` in native SQL |
| Object mapping | `ObjectMapper` for JSON | Same `ObjectMapper` approach |
